# Feature: Item CRUD

## Status

Completed

## Summary

Deliver the first usable DevStash workflow: developers can create, view, edit, and
delete saved text items from the React application, with FastAPI persisting them in
PostgreSQL through a versioned migration.

## Goals

- Define one consistent item record for the initial text-based DevStash item types:
  snippet, prompt, command, and note.
- Provide a documented, typed JSON API to create, list, retrieve, update, and delete
  items.
- Persist items in PostgreSQL using SQLAlchemy models, repositories, and an Alembic
  migration.
- Add an accessible React interface for listing, creating, editing, and deleting
  items, including explicit loading, empty, validation, and error states.
- Preserve a clear backend API boundary and typed frontend API client for later
  routing, collections, tags, search, and authorization features.

## Non-Goals

- Add collections, tags, favorites, pins, search, filtering, sorting controls, or
  pagination.
- Add user accounts, authentication, authorization, multi-tenancy, or sharing. Until
  an account feature is specified, every item belongs to the single local workspace.
- Support links, files, images, external metadata fetching, or binary uploads.
- Render Markdown, execute commands, syntax-highlight snippets, or run AI actions.
- Redesign the complete dashboard, add client-side routing, or introduce global state
  management.
- Add a dedicated item-edit route or navigate away from the dashboard to edit an
  item.

## User Story

As a developer, I want to save and maintain reusable snippets, prompts, commands,
and notes so that I can return to useful development knowledge in one place.

## API Contract

All endpoints are unauthenticated in this feature and return JSON. Routes are served
under `/api` by FastAPI. Vite forwards browser `/api/*` requests unchanged. The
process-level `/health` endpoint remains outside the product API namespace and has
its own unchanged development proxy.

### Item representation

```json
{
  "id": "0f5c14b5-49c4-4a64-afd4-1cba7284ffdf",
  "title": "Restart local services",
  "content": "docker compose restart",
  "item_type": "command",
  "language": null,
  "created_at": "2026-08-26T09:30:00Z",
  "updated_at": "2026-08-26T09:30:00Z"
}
```

- `id` is a server-generated UUID.
- `title` is required, trimmed, and 1–200 characters.
- `content` is required and 1–50,000 characters; whitespace-only content is invalid.
- `item_type` is required and one of `snippet`, `prompt`, `command`, or `note`.
- `language` is optional, trimmed, and at most 64 characters. It is accepted only for
  `snippet`; API requests that set it for another type receive a validation error.
- Timestamps are server-generated UTC datetimes and serialized in ISO 8601 form.

### `POST /api/items`

- Request: `title`, `content`, `item_type`, and optional `language` using the rules
  above.
- Success: `201 Created` with the item representation and a `Location` header for
  `/api/items/{id}`.
- Invalid input: `422 Unprocessable Entity` using FastAPI's validation response.

### `GET /api/items`

- Success: `200 OK` with a JSON array of all items, ordered by `updated_at`
  descending and then `id` descending for deterministic ties.
- An empty workspace returns `[]`.
- This initial endpoint deliberately has no filtering or pagination parameters.

### `GET /api/items/{id}`

- Success: `200 OK` with the item representation.
- Unknown or malformed ID: `404 Not Found` with a stable, non-sensitive detail.

### `PATCH /api/items/{id}`

- Request: a non-empty object containing any of `title`, `content`, `item_type`, or
  `language`. The complete resulting item must satisfy the item representation
  rules; changing away from `snippet` requires `language` to be cleared.
- Success: `200 OK` with the updated item and a later `updated_at` value.
- Invalid input: `422 Unprocessable Entity`; unknown or malformed ID: `404 Not Found`.

### `DELETE /api/items/{id}`

- Success: `204 No Content`.
- Unknown or malformed ID: `404 Not Found`.
- Deletion is permanent; a future recovery mechanism requires its own specification.

The existing `GET /health` contract remains unchanged.

## Data Model

Add an `items` table through an Alembic migration with:

- UUID primary key `id` generated by the application;
- required `title`, `content`, and `item_type` columns;
- nullable `language` column;
- required timezone-aware `created_at` and `updated_at` timestamp columns;
- database constraints that restrict `item_type` to the four supported values and
  prevent empty title or content values after trimming at the API boundary;
- an index supporting the initial descending updated-time listing.

Use SQLAlchemy 2.x typed mappings and the existing shared declarative base. Keep ORM
models separate from Pydantic request/response models. The migration must implement
both upgrade and downgrade paths.

## Security and Privacy

- No authentication is introduced; the API must make no claim that workspace data is
  private or user-scoped until the authentication feature exists.
- Validate all request input at the API boundary and use SQLAlchemy expressions and
  bound parameters for persistence access.
- Return stable client-safe errors; do not leak SQL statements, connection details,
  stack traces, or database credentials.
- Render item text as text in the UI. Do not inject item content as HTML or execute
  saved command content.
- Keep PostgreSQL integration data in the existing uniquely named disposable test
  databases and never run destructive cleanup against development data.

## Decisions and Open Questions

Selected decisions:

- The first item slice supports only the four text-based types already named in the
  project overview.
- `language` is optional metadata for snippets only; it is not inferred or validated
  against a predefined language catalogue.
- UUIDs are generated by the application rather than relying on a database extension.
- `PATCH` is used for partial edits; create and update return the canonical persisted
  representation.
- The unauthenticated initial workspace is intentional and temporary; adding an
  owner column before the accounts feature would create an invented user contract.
- The initial list is intentionally unpaginated. Search, filtering, and pagination
  will be defined together in their later feature spec.
- FastAPI exposes product endpoints under the canonical `/api` namespace. Vite
  forwards `/api/*` and `/health` without rewriting paths, so browser, OpenAPI, test,
  and production URLs remain consistent.

Selected UI decision:

- Item details and editing use a drawer on the current page. Editing does not have a
  dedicated route. Saving refreshes the drawer and item list in place; canceling
  returns the drawer to its read-only detail state.

## Implementation Notes

- Register an `APIRouter` from the FastAPI application and retain `/health` at its
  existing URL.
- Use the session dependency from `src/devstash/core/`; repositories must not create
  engines or sessions directly.
- Make write transaction ownership explicit in the item service. A failed operation
  must roll back before the session closes.
- Create frontend API functions and TypeScript contracts outside presentational
  components. Use existing Tailwind and local shadcn/ui foundations before adding UI
  dependencies.
- Reuse the dashboard's established responsive drawer interaction and preserve
  accessible focus containment, Escape handling, and focus restoration.
- Keep the active implementation limited to this spec; do not prebuild collection,
  tag, search, or account abstractions.
